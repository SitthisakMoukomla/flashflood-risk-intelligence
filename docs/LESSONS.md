# บทเรียนจากการสร้างจริง

เอกสารนี้เก็บสิ่งที่**ผิดพลาดแล้วแก้** ไม่ใช่วิธีที่ถูกต้องสำเร็จรูป
เพราะงานจริงคือการเจอทางตันแล้วหาทางออก ซึ่งหาอ่านจากคอร์สทั่วไปไม่ได้

แต่ละข้อมีโครงเดียวกัน: **อาการ → สาเหตุ → วิธีแก้ → บทเรียนทั่วไป**

---

## 1. ทำ raster แล้วแย่กว่าเดิม

**อาการ** — ผู้ใช้บ่นว่าโพลิกอนน้ำท่วม "เป็นเหลี่ยมๆ" จึงเปลี่ยนไปวาดเป็นภาพ raster
ผลคือเหลี่ยม*กว่าเดิม* เป็นบล็อกใหญ่โตกว่าน้ำท่วมจริง

**สาเหตุ** — เลือกความละเอียด 220 ม. เพื่อให้ทั้งประเทศอยู่ในไฟล์เดียวที่เบราว์เซอร์
decode ไหว แต่ 220 ม. ใหญ่กว่าน้ำท่วมส่วนใหญ่ที่ตรวจพบ pixel เดียวจึงกินพื้นที่
เกินจริง — วัดได้ว่าขยายพื้นที่ถึง **16 เท่า**

**วิธีแก้** — เปลี่ยนเป็น tile pyramid (z6–z12) ความละเอียดสุด 36 ม. เก็บเป็น
PMTiles ไฟล์เดียว เบราว์เซอร์ดึงเฉพาะ tile ที่มองเห็นด้วย HTTP range request
โหลดจริงราว 19 KB ต่อครั้ง แทนที่จะเป็นทั้งไฟล์

**บทเรียน** — "ไฟล์เดียวครอบทั้งประเทศ" บังคับให้ใช้ความละเอียดเดียวทุกระดับซูม
ซึ่งเป็นไปไม่ได้ที่จะดีทั้งสองทาง tile pyramid มีไว้แก้ปัญหานี้โดยเฉพาะ
**และ**: ถ้าแก้แล้วผลแย่ลง ต้องยอมรับและบอกตรงๆ ไม่ใช่อ้างว่าดีขึ้น

---

## 2. สถานีวัดน้ำ 605 แห่งขึ้นเป็นจุดเทา

**อาการ** — โทรมาตรกรมชลประทานส่วนใหญ่แสดงเป็น "ไม่มีข้อมูล" ทั้งที่เป็นเครือข่าย
ใหญ่ที่สุดในระบบ (912 สถานี)

**สาเหตุ** — โค้ดใช้ฟิลด์ `storage_percent` ฟิลด์เดียวในการกำหนดสี แต่ ชป. ส่งค่านี้มา
แค่ 34% ทั้งที่ส่งระดับน้ำ ระดับตลิ่ง และท้องน้ำมาครบ — ThaiWater คำนวณให้ไม่ได้
เพราะ ชป. ปล่อยฟิลด์ `min_bank` เป็น 0

**วิธีแก้** — คำนวณเองจากค่าที่มี `(ระดับน้ำ − ท้องน้ำ) ÷ (ระดับตลิ่ง − ท้องน้ำ)`
ตรวจสอบกับ 795 สถานีที่เผยแพร่ค่าอยู่แล้ว ได้ค่าคลาดเคลื่อนกลาง **0.005 จุด**
จุดเทาลดจาก 631 เหลือ 26

**กับดักระหว่างทาง** — ตอนแรกใช้ค่าต่ำสุดของทั้งสามฟิลด์ ผิดหนักที่ 4 สถานี
(สถานีหนึ่งได้ 462% ทั้งที่จริง 84%) เพราะบางสถานีบันทึกระดับตลิ่งคนละระบบ
อ้างอิงกับท้องน้ำ ต้องให้ `min_bank` มาก่อนเสมอเหมือนที่ ThaiWater ทำ

**บทเรียน** — อย่าเชื่อฟิลด์เดียว ให้ดูว่าข้อมูลดิบมีอะไรมาให้บ้าง
และ**ตรวจสูตรที่คิดเองกับข้อมูลที่มีเฉลยเสมอ** ก่อนเอาไปใช้กับข้อมูลที่ไม่มีเฉลย

## 3. Deploy ข้อมูลทดสอบขึ้นเว็บจริง

**อาการ** — เว็บแสดงน้ำท่วม 83 ไร่ ทั้งที่ของจริง 791,647 ไร่

**สาเหตุ** — `vercel build` อ่านไฟล์จาก**เครื่อง** ไม่ใช่จาก git ตอนนั้นมีไฟล์
จากการทดสอบ 8 แผ่นค้างอยู่ ระบบจึงเอาไปขึ้น production ทั้งที่ git ถูกต้อง

**วิธีแก้** — เขียน `scripts/preflight.mjs` ตรวจก่อน deploy ทุกครั้ง:
หน้าต่างเวลาครบ 7 วันมั้ย ดาวเทียมผ่านกี่รอบ พื้นที่สมเหตุสมผลมั้ย ไฟล์ tile ใหญ่พอมั้ย
ผูกกับ `npm run deploy` ถ้าไม่ผ่านจะหยุดตั้งแต่ต้น

**บทเรียน** — build ผ่าน ≠ ข้อมูลถูก ระบบ deploy ที่อ่านจาก working directory
เป็นกับดักที่มองไม่เห็น ต้องมีด่านตรวจข้อมูลแยกจากด่านตรวจโค้ด

---

## 4. GEE โควตาหมดกลางทาง

**อาการ** — Google Earth Engine เข้าสู่ restricted mode งาน export ค้างคิวไม่มีกำหนด

**สาเหตุ** — โควตา compute รายเดือนของ noncommercial tier หมด จากงานอื่นในบัญชีเดียวกัน

**วิธีแก้** — ย้ายไปคำนวณเองจากข้อมูลเปิดที่ไม่มีโควตา: Copernicus DEM,
HydroSHEDS, ESA WorldCover, CHIRPS, JRC Global Surface Water — ทั้งหมดโหลดตรง
ไม่ต้องมีบัญชี

**บทเรียน** — บริการฟรีที่ต้องล็อกอินคือ**จุดพึ่งพาที่ควบคุมไม่ได้**
ถ้าระบบต้องทำงานอัตโนมัติทุกวัน ให้เลือกแหล่งที่ไม่มีโควตาก่อนเสมอ

## 5. Cron ล้มเงียบมา 3 เดือน

**อาการ** — ข้อมูลฝนบนแผนที่ค้างอยู่ที่ 9 พ.ค. ทั้งที่ตั้ง cron รายวันไว้

**สาเหตุ** — workflow เรียกสคริปต์ที่ต้องใช้ไฟล์ระดับกลางซึ่งอยู่ใน `.gitignore`
บนเครื่อง runner จึงไม่มีไฟล์นั้น สคริปต์ล้มทุกครั้ง แต่ไม่มีใครดู log

**วิธีแก้** — เปลี่ยนไปเรียกสคริปต์ที่ไม่ต้องพึ่งไฟล์ที่ไม่ได้ commit

**บทเรียน** — งานอัตโนมัติที่ไม่มีคนดูจะล้มเงียบ ควรออกแบบให้**ความล้มเหลวมองเห็นได้**
(เช่น ให้เว็บแสดงเวลาอัปเดตล่าสุดเสมอ ถ้าค้างจะสังเกตได้)

---

## 6. ตัวเลขน้ำท่วมเกินจริง เพราะนับแม่น้ำด้วย

**อาการ** — ผู้ใช้ทักว่าโพลิกอนน้ำท่วมทับแหล่งน้ำถาวร

**สาเหตุ** — ตรวจครั้งแรกที่ระดับ**โพลิกอน** พบทับแค่ 0.7% จึงสรุปว่าสะอาดแล้ว
ซึ่งผิด เพราะแม่น้ำวิ่งอยู่*กลาง*โพลิกอนใหญ่ วิธีวัดแบบนั้นมองไม่เห็น

**วิธีแก้** — ลบที่ระดับ **pixel** ก่อนแปลงเป็นรูปทรง ใช้ JRC Global Surface Water
เกณฑ์มีน้ำ ≥6 เดือน/ปี ตัดออกได้ **409 ตร.กม. หรือ 23%** ของที่ตรวจพบ

**บทเรียน** — หน่วยที่ใช้วัดกำหนดสิ่งที่มองเห็น ถ้าวัดหยาบกว่าปัญหา จะสรุปว่าไม่มีปัญหา
และเมื่อผู้ใช้ทักว่าผิด ให้ตรวจซ้ำด้วยวิธีอื่น อย่ายืนยันด้วยวิธีเดิม

---

## 7. งานช้ากว่าที่ควร 3 เท่า

**อาการ** — pipeline ใช้เวลา 42 วินาทีต่อแผ่น รวมเกือบ 2 ชั่วโมง

**สาเหตุ** — reproject ภาพทั้ง 15,000 × 15,000 pixel ทุกครั้ง ทั้งที่น้ำท่วมกิน
พื้นที่แค่ไม่กี่พัน pixel เสียแรงคำนวณไปกับพื้นที่ว่าง 99%

**วิธีแก้** — ตัดกรอบเฉพาะบริเวณที่มีน้ำท่วมก่อน reproject เหลือ 14 วินาที/แผ่น
ผลลัพธ์เหมือนเดิมทุกประการ

**บทเรียน** — ก่อน optimize ให้วัดก่อนว่าเวลาหมดไปกับอะไร ในงาน raster
คำตอบมักคือ "ประมวลผลพื้นที่ที่ไม่มีข้อมูล"

## สิ่งที่ยึดตลอดทั้งโปรเจกต์

**1. ไม่มีข้อมูล ≠ ไม่มีความเสี่ยง** — จุดที่ยังไม่เคยวัดจะเว้นว่างไว้ ไม่ระบายสีเขียว
เพราะการทาสีเท่ากับอ้างว่า "ตรวจแล้วปลอดภัย"

**2. บอกข้อมูล ไม่สั่งการ** — แอปไม่มีคำว่า "อพยพ" หรือ "ให้ทำ X"
การตัดสินใจเชิงปฏิบัติเป็นของหน่วยงานในพื้นที่

**3. บอกความไม่แน่นอนเสมอ** — ทุกเลเยอร์แสดงเวลาที่วัด และระบุข้อจำกัด
(ดาวเทียมผ่านทุก 1–3 วัน เรดาร์มองไม่เห็นน้ำใต้เรือนยอดไม้)

**4. ยืนยันด้วยหลักฐานก่อนเชื่อ** — ทุกครั้งที่แก้เสร็จ ต้องวัดผลจริง
ไม่ใช่ดูว่า build ผ่าน
